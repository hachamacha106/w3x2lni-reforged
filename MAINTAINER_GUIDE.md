# Maintainer guide — Codex, GitHub and releases

This repo is prepared from the **W3x2lni Reforged 1.0.0 source snapshot**. Its original upstream Git history and all nine *pinned gitlink* submodules are retained. The uploaded Windows ZIP is an application release, **not** the source to commit.

## 1. First setup (Windows: PowerShell)

Prerequisites: [Git for Windows](https://git-scm.com/download/win), [GitHub CLI](https://cli.github.com/), [Python 3](https://www.python.org/downloads/), and [Codex](https://github.com/openai/codex). Install Codex with `npm install -g @openai/codex` if Node.js/npm is available, or use the Windows installer listed in the Codex project's README.

1. **Extract this entire starter ZIP** to a normal folder, e.g. `C:\Projects\w3x2lni-reforged`. Enable viewing hidden files and verify it contains `.git`, `.gitmodules`, `AGENTS.md` and `release.json`. It is *already* a Git repository and is on branch `main`. **Do not run `git init`.**
2. Open PowerShell in that folder, then configure your new GitHub repository identifier:

   ```powershell
   python tools/configure_repository.py YOUR_GITHUB_NAME/w3x2lni-reforged
   ```

   This updates `release.json` and active project links. Review the diff; historical credits should remain intact. Do **not** tag 1.0.0 again.
3. Set up Git identity and the GitHub CLI on your machine if necessary:

   ```powershell
   git config --global user.name "YOUR NAME"
   git config --global user.email "YOUR VERIFIED GITHUB EMAIL"
   gh auth login
   git status
   git diff --check
   ```

4. Create a **new empty** GitHub repository with your chosen name (omit autogenerated README/license/.gitignore; these already exist). For a public repo, review third-party data/licensing before upload. From the folder:

   ```powershell
   git add AGENTS.md MAINTAINER_GUIDE.md .github/workflows/ci.yml .github/workflows/build.yml .gitignore README.md tools/configure_repository.py release.json docs/en-us/reforged-release.md docs/en-us/current-warcraft.md
   git commit -m "chore: prepare Codex and GitHub maintenance"
   git remote add origin https://github.com/YOUR_GITHUB_NAME/w3x2lni-reforged.git
   git push -u origin main
   ```

   **IMPORTANT:** The prepared directory has no remote by design. Use your actual repo slug consistently in both the Python configure step and remote URL. If you change files beyond those listed, stage/review them consciously. You can use `gh repo create YOUR_GITHUB_NAME/w3x2lni-reforged --public --source=. --remote=origin --push` *instead of* manually creating the GitHub repo and adding/pushing the remote; do not do both.
5. Fetch pinned dependencies, required for native builds / the release pipeline:

   ```powershell
   git submodule update --init --recursive
   git submodule status
   ```

   The original source ZIP had **empty `3rd/` directories**, not the dependency contents. Git's pinned submodule commits must be fetched. Do not manually populate those directories from arbitrary ZIPs.
6. On GitHub, confirm the **CI quick checks** workflow passes on `main`. Enable Actions and Issues if prompted. Under Settings → Branches / Rulesets, protect `main` with required PR reviews and a passing `CI quick checks` status, after the first check has run successfully.

> Repository setup must be run with a real `OWNER/REPO` *before* the initial push. `release.json` still names the previous repository until configured.

## 2. Day-to-day Codex workflow

Codex CLI (or the VS Code Codex extension) reads `AGENTS.md` automatically. In your repo directory:

```powershell
# Switch to a dedicated branch for each change
git switch main
git pull --ff-only
git switch -c fix/my-map-bug
codex
```

Example Codex request:

> Investigate this W3I conversion bug, find the relevant Lua parser, add a regression test, implement the smallest safe fix, and run the fast checks described in AGENTS.md. Do not push or tag anything. Summarize the diff and compatibility risks.

Review with `git diff` and `git status`. When satisfied:

```powershell
git add -A
git diff --cached --check
git commit -m "fix: preserve W3I field during conversion"
git push -u origin fix/my-map-bug
gh pr create --base main --fill
```

Wait for CI, review the pull request, and merge it into `main`. Avoid asking Codex to bypass CI or upload the portable binaries to Git.

## 3. Build and release workflow

- `.github/workflows/ci.yml` runs fast Python static/packaging tests on pushes and PRs to `main`.
- `.github/workflows/build.yml` runs the **full expensive release checks** on `v*` tags or manually via `workflow_dispatch`. It downloads the byte-pinned upstream 2.7.3 Windows runtime, builds a candidate with source provenance, runs compatibility tests on Linux and native Windows smoke tests, and for matching tags creates a **draft GitHub release**. Manual dispatch does not create a draft.
- GitHub-hosted runners need to download the pinned runtime and pinned submodules from their upstream locations. CI success is not assured until a genuine Actions run completes.
- GitHub Actions need no OpenAI API key: Codex runs locally; Actions just run your tests/release scripts. Keep credentials out of Git.

**Before making a new release**, update:

1. `release.json`: `version`, `display_version`, `tag`, `asset_name`, `archive_root`; leave `repository` set to *your* actual GitHub slug.
2. `script/share/changelog.lua`: the in-app version string and relevant notes.
3. `CHANGELOG.md`: changes since the previous version.
4. `docs/releases/X.Y.Z.md`: user-facing release notes used by the draft script.

Then merge version changes into main and wait for CI. Create and push a tag matching `release.json`, e.g. `git tag -a v1.0.1 -m "W3x2lni Reforged 1.0.1"` then `git push origin v1.0.1`. Use the Actions tab to confirm **all** Linux and Windows validations pass; verify the draft release assets and test the portable GUI on a Windows machine with representative Warcraft III maps. Publish the draft manually.

**Version warning:** a tag `v1.0.0` was already the previous project's release. Your first new code release should use a *new* version, such as 1.0.1, once its metadata, changelog and release notes are actually updated. Never republish the exact upstream 1.0.0 binaries under an untested new version.

## 4. Where changes typically go

- Lua conversion, formats, GUI, reports: `script/`
- Warcraft data version and metadata: `data/` (preserve bytes and provenance)
- Compatibility/regression coverage: `test/compat/` and `test/unit_test/`
- Release/build/checks: `make/`, `test/release/`, `.github/workflows/`
- Native C++: `c++/` and pinned `3rd/` submodules (**not rebuilt for the current 1.0.0 release process**)

See `docs/en-us/reforged-release.md` for the original full release-process details and `docs/en-us/current-warcraft.md` for format/data constraints. Keep upstream attribution and GPLv3 licensing.

## 5. Maintaining the 1.1 native build and conversion interface

Use GitHub Desktop to review the feature branch, commit the reviewed source and
push it only after approval. The full **Reforged release checks** workflow now
first builds and probes Windows x86 StormLib 9.40 with static zlib 1.3.2. The
Linux package job consumes that exact artifact, builds the same dependency pins
for tests, runs all original 14 suites plus the pjass and lossless suites, and
locks the final runtime fingerprint. Windows smoke tests exercise the exact ZIP.
Manual dispatch still creates no release draft; a matching version tag does.

The old upstream-runtime verification route remains available for historical
packages. Version 1.1+ release packaging requires --native-runtime and --pjass.
Only bin/stormlib.dll may be rebuilt; only bin/pjass.exe may be added. Retained
files still match the byte-pinned upstream archive. Build settings, source pins,
ABI evidence and component hashes must match. Never substitute a locally found
DLL or silently fall back to bundled old zlib.

For a local native build through graphical installation:
1. Open **Visual Studio Installer**.
2. Under Visual Studio 2022, click **Modify**.
3. Select **Desktop development with C++**, including MSVC v143 x86/x64,
   a Windows SDK, and **C++ CMake tools for Windows**.
4. Click **Modify** to install. Codex can run the build and tests afterward.
GitHub-hosted Windows runners provide the build environment for Actions.

CascLib modernization is a separate follow-up. Require extraction from a real
Warcraft installation; mocks and a DLL load test do not establish CASC coverage.
The experimental Analyze/Optimize archive actions are retired from the GUI and
public CLI. Keep their lower-level safety code and regression tests: the private
`test/release/archive_worker.lua` entry checks the rebuilt StormLib DLL without
restoring those actions. The existing LNI, OBJ and SLK conversions remain the
public map workflow. pjass is report-only for user maps; release regression fixtures must still pass
their required checker assertions. Keep manual editor/game acceptance separate
from compiler and archive verification.

See docs/releases/1.1.0.md for user-visible behavior and constraints.


### Review the 1.1 work in stages

Keep the review order: archive write/close failures; native build, pins and
provenance; pjass service and conversion checks; conversion GUI and retired-action
checks; release metadata, notices and acceptance evidence. The integration branch may
hold the whole candidate, but review and commit these as scoped changes before
opening small PRs. Dependency changes and their ABI/provenance checks belong
together. Do not publish a partially wired package.

All 16 extracted-package suites remain required, including the dormant archive
safety suite. Native smoke tests retain payload equality, unknown-data preservation,
Unicode, cancellation and output-race checks through private regression helpers.
Their evidence is labeled internal-only; successful checks do not mean an archive
Analyze/Optimize action is available or manually accepted. No public command or
release note should advertise those retired actions.

CascLib modernization and extra compression features remain separate follow-ups.
